# 导入菜品申请同步模板设计

## 1. 目标

商户从平台模板菜库导入菜品后，可以继续独立维护自己的菜品副本。当商户认为当前副本的信息更准确或更完善时，可以从该菜品直接发起“申请同步到模板”。系统根据商户菜品实时数据生成模板修改申请，仍由平台管理员审核；审核通过后才覆盖平台模板，不直接影响其他商户已经导入的菜品副本。

## 2. 范围

一期覆盖以下终端：

- 微信小程序商户端：在已导入菜品的管理列表和编辑页提供申请入口。
- PC 商户后台：在已导入菜品列表和编辑区域提供申请入口。
- 平台管理端：复用现有模板菜品修改审核列表、详情、通过和驳回能力。
- Java Spring Boot 后端：增加从商户菜品构建完整模板快照并提交审核的专用接口。

不新增数据库表，不改变现有模板审核状态机，不把商户制作步骤同步到平台模板。

## 3. 业务规则

### 3.1 可发起条件

- 当前用户必须拥有当前商户的后台权限。
- 菜品必须属于当前商户。
- 菜品必须存在 `source_template_id`，即由平台模板导入；手工创建菜品不能发起同步。
- 来源模板必须仍然存在。
- 同一商户、同一模板只能存在一条 `PENDING` 申请。
- 商户菜品至少包含一项有效食材。

### 3.2 字段覆盖规则

从当前商户菜品覆盖到目标模板快照的字段：

| 商户菜品字段 | 模板目标字段 | 规则 |
| --- | --- | --- |
| `name` | `name` | 完整覆盖 |
| `description` | `description` | 完整覆盖 |
| `image_url` | `imageUrl` | 完整覆盖 |
| `base_price` | `referencePrice` | 完整覆盖 |
| 菜品食材名称、用量、单位、计算方式 | `ingredients` | 按当前菜品食材顺序整体覆盖 |

继续沿用来源模板当前值的字段：

- `categoryId`
- `imageSourceUrl`
- `imageAuthor`
- `imageLicense`
- `tasteTags`
- `mealTags`
- `sortOrder`
- `enabled`

食材分类不在菜品食材明细表中。系统按名称查询当前商户食材字典，命中时使用字典分类；未命中时优先沿用来源模板中同名食材分类，仍未命中时使用统一分类“其他”。制作步骤属于商户私有操作资料，不进入模板快照。

### 3.3 审核与版本

- 提交时锁定来源模板并记录其当前 `version` 和原始快照。
- 自动生成的目标快照使用现有模板快照版本 `schemaVersion=1`。
- 审核通过时继续执行现有乐观版本检查；模板已被其他申请更新时返回冲突，不覆盖新版本。
- 审核通过后整体更新模板主信息和食材，模板版本加一。
- 审核驳回、商户撤回和通知中心沿用现有逻辑。
- 平台模板更新后不反向覆盖任何商户菜品副本。

## 4. 接口设计

### 4.1 提交同步申请

`POST /api/merchant/dishes/{dishId}/template-change-requests`

请求体：

```json
{
  "submitNote": "补充了更准确的配料和用量"
}
```

`submitNote` 可空，最多 500 个字符。快照由服务端从实时数据库生成，前端不能传入或篡改模板保留字段。

成功响应复用 `DishTemplateChangeSubmitView`：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "requestId": 88,
    "status": "PENDING",
    "submittedAt": "2026-08-15T21:00:00"
  }
}
```

典型错误：

- `菜品不存在或无权操作`
- `该菜品不是从平台模板导入，不能申请同步`
- `来源模板菜品不存在`
- `当前菜品至少需要1项食材后才能申请同步`
- `本商户对该模板已有待审核修改申请`
- 现有字段校验对应的明确错误消息

### 4.2 菜品查询响应补充

商户菜品列表和详情增加：

- `sourceTemplateId`：来源模板 ID，手工创建菜品为空。
- `templateImported`：是否为模板导入菜品，方便前端直接控制入口显示。

不把该字段暴露为菜品创建或编辑请求参数，避免手工伪造模板关联。

## 5. 后端结构

- `DishController`：增加提交同步申请接口和 springdoc 描述。
- `ImportedDishTemplateSyncRequest`：只接收申请说明。
- `DishTemplateChangeRequestService`：增加 `submitFromImportedDish` 方法。
- `DishTemplateChangeRequestServiceImpl`：读取商户菜、食材字典、来源模板和模板食材，按字段规则构建快照，再复用统一申请落库流程。
- `DishMapper`：复用商户隔离的菜品、菜品食材和食材字典查询；必要时增加按名称批量查询能力。
- `DishView`、`DishDetailView`：返回来源模板标识。

申请创建必须在一个事务中完成。服务端先验证商户菜所有权，再锁来源模板，避免未授权请求通过模板 ID 探测平台数据。

## 6. 前端交互

### 6.1 微信小程序商户端

- 仅当 `templateImported=true` 时显示“同步模板”操作。
- 点击后弹出确认框，说明“提交后进入平台审核，不会立即修改系统菜库”。
- 允许填写可选申请说明。
- 提交期间禁用重复点击。
- 成功后提示“已提交模板审核”，跳转到对应申请详情。
- 对手工菜品、重复待审核、模板不存在等错误直接展示后端明确消息。

### 6.2 PC 商户后台

- 菜品表格的已导入菜品增加“同步模板”。
- 当前编辑的是已导入菜品时，编辑区底部也显示该入口。
- 使用确认对话框收集可选说明并提交。
- 成功后跳转到模板修改申请详情或申请列表，并刷新菜品状态。

### 6.3 状态展示

一期不在菜品表增加冗余审核状态字段。提交成功后进入现有“模板修改申请”页面查看 `PENDING`、`APPROVED`、`REJECTED`、`WITHDRAWN` 状态。

## 7. 安全与错误处理

- 后端以登录上下文中的 `merchantId` 查询菜品，不接受前端传商户 ID。
- 所有请求参数错误、资源不存在、权限不足和状态冲突使用统一 `ApiResponse`。
- 快照字段仍通过 `DishTemplateSnapshotValidator` 做完整业务校验。
- 图片必须是系统可访问的真实图片地址；后端不生成占位图或模拟图片。
- 日志不记录令牌、用户隐私或完整请求快照。

## 8. 测试与验收

后端测试：

- 已导入菜品能构建正确快照并产生 `PENDING` 申请。
- 商户菜覆盖五类字段，模板专属字段保持不变。
- 食材分类按“字典、原模板同名项、其他”顺序回退。
- 手工菜品、越权菜品、空食材、来源模板不存在和重复待审核均返回明确错误。
- 审核版本冲突和原有审核流程回归通过。

前端测试：

- 手工菜品不显示同步入口，导入菜品显示入口。
- 小程序和 PC 均调用专用接口，不在前端拼装模板快照。
- 成功后进入真实申请详情，失败时展示后端消息，重复点击被拦截。

完成标准：后端单元测试、前端测试、PC 构建和 UTF-8 扫描全部通过，接口文档与前端 API 指南同步更新。
