# 餐篮提交必填信息提醒设计

## 目标

用户点击“提交订单”时，即使下单条件未满足也必须收到显眼、可理解的反馈，不能只依赖页面底部红字。校验失败不得调用提交接口。

## 交互

- 餐篮处于可操作状态时，“提交订单”按钮保持可点击；仅在正在修改或提交时禁用并显示处理中状态。
- 点击后集中校验所有阻断条件：今日预约已结束、餐篮为空、预计用餐时间无效、存在不可用菜品、配送模式未选择有效地址。
- 校验失败使用 `wx.showModal` 展示确认式对话框，标题为“还不能提交订单”，正文逐项列出问题，不显示取消按钮。
- 用户确认后通过 `wx.pageScrollTo` 定位到第一个问题区域：时间、餐篮菜品或取餐方式。
- 现有页面红字继续保留，作为常驻辅助信息；弹窗和定位是主要反馈。
- 校验通过后沿用现有订单提交、成功提示、新餐篮刷新和订单页跳转流程。

## 代码边界

- 新建纯函数工具，输入餐篮页面状态，输出 `{ issues, target }`，避免把校验规则散落在页面事件中。
- 页面为时间、取餐方式、已选菜品区域添加稳定锚点。
- `submitOrder` 先调用纯函数；有问题时弹窗并定位，没有问题才调用后端。
- 底部操作栏不再用 `canSubmit` 禁止点击，只用 `mutationBusy` 控制防重复提交。

## 校验顺序与提示

1. 今日预约已结束：`今天已停止预约，请明天再来`
2. 餐篮为空：`请先选择至少一道菜品`
3. 预计用餐时间无效：`请选择今天的预计用餐时间`
4. 存在不可用菜品：`餐篮中有不可用菜品，请减少到 0 后再提交`
5. 配送无地址：`请选择配送地址`

未知原因导致 `canSubmit=false` 时，追加通用提示 `请先完善下单信息`，确保任何阻断都不会静默。

## 测试

- 纯函数测试覆盖单个问题、多个问题、顺序、定位目标和可提交状态。
- 页面契约测试覆盖按钮仍可点击、提交前弹窗、确认后定位、校验失败不调用接口。
- 运行小程序完整测试，确认现有餐篮、订单和底部操作栏行为无回归。
