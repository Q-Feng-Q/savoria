# 家庭钱包按需初始化设计

## 问题

`GET /family/wallet` 路由已注册，但已加入家庭的用户仍可能收到 HTTP 404。钱包表由历史迁移流程填充，而当前迁移模式为 `OFF`，家庭创建流程也不保证创建 `family_wallets` 记录，因此业务层抛出“家庭钱包不存在”。

## 目标

在不执行批量迁移、不修改已有钱包余额的前提下，为缺少钱包记录的有效家庭按需创建零余额家庭钱包，并让查询与订单资金操作使用相同的账户存在性保障。

## 方案

### 持久化

在 `FamilyWalletMapper` 增加幂等方法 `insertAccountIfMissing(familyId)`。SQL 使用：

```sql
insert ignore into family_wallets(family_id, available_amount, frozen_amount)
select id, 0, 0
from families
where id = #{familyId} and status = 'active'
```

该语句只会为存在且启用的家庭创建账户；已有记录不更新，余额和版本均不改变；并发请求依赖家庭钱包主键和 `insert ignore` 收敛为一条记录。

### 初始化器

新增独立的 `FamilyWalletAccountInitializer` 组件，使用 `@Transactional(propagation = REQUIRES_NEW)`：

1. 先普通查询钱包；已有钱包立即返回，不执行重复插入。
2. 钱包缺失时执行 `insertAccountIfMissing`。
3. 初始化事务在调用方继续之前独立提交。

该组件必须通过 Spring 代理从钱包服务调用，不能写成同类私有方法自调用。这样缺失钱包的插入不会发生在资金行锁事务内部，也不会让已有钱包的并发资金操作先竞争重复键锁再升级为排他锁。

### 服务

`FamilyWalletServiceImpl.get(familyId)`：

1. 先查询钱包，保持正常读路径无额外写入。
2. 缺失时调用独立初始化器，再查询一次。
3. 二次查询仍缺失时返回现有“家庭钱包不存在”错误，覆盖无效或停用家庭。

`FamilyWalletServiceImpl.lockAccount(familyId)`：

1. 在获取钱包行锁之前始终调用独立初始化器；其新事务完成并提交后才返回。
2. 调用方资金事务随后执行 `select ... for update`，避免“先锁不存在的主键范围、再并发插入”形成间隙锁竞争。
3. 仍缺失时返回现有错误。

这样查询、冻结、扣款、释放和退款都共享相同保障，不产生只修查询、不修下单的分叉行为。

## 数据安全

- 不运行家庭钱包迁移器或任何批量数据脚本。
- 不读取、汇总或清空个人钱包。
- 不覆盖已有家庭钱包的可用余额、冻结余额和版本。
- 每次只处理当前业务请求关联的单个有效家庭。
- 对不存在或停用的家庭不创建新钱包。
- 家庭端身份上下文由 `IdentityContextMapper` 以 `f.id` 和 `f.status='active'` 实时生成，停用家庭不会得到 `familyId`，因此不能进入家庭钱包接口。商户入口也通过有效家庭归属查询授权。
- 底层钱包服务不删除或屏蔽停用家庭已经存在的钱包；订单取消、结算和退款可能仍需处理历史资金。这一行为与家庭端访问控制分层处理。

## 并发与事务

- 普通查询采用“先查、缺失时调用独立初始化事务、再查”。
- 资金操作已在事务中执行，但初始化器使用 `REQUIRES_NEW` 暂停外层资金事务并独立提交；外层恢复后才执行 `select ... for update`，不对不存在的主键先加间隙锁。
- 已有钱包的初始化器路径只做普通查询，不执行 `insert ignore`；已有钱包的资金并发仍由原 `select ... for update` 序列化，不引入重复键锁升级。
- 同一家庭并发首次初始化时，一个请求插入，其他请求等待唯一主键判定后忽略重复插入，再读取或锁定同一账户。
- 不增加吞掉数据库异常的通用重试；真实 MySQL 并发测试必须证明首次查询和首次资金操作无死锁或序列化失败。若测试发现数据库级失败，再单独设计有界重试，不在本次修复中预设。

## 测试

- Mapper SQL 契约：必须从 `families` 选择有效家庭，使用 `insert ignore`，且初始余额均为 0。
- 服务测试：钱包已存在时不初始化；钱包缺失时初始化后返回零余额账户；无效家庭初始化后仍缺失时继续返回 404。
- 锁定路径测试：钱包缺失时初始化后可获取锁定账户，确保下单资金流程同样有效。
- 身份契约测试：家庭端上下文只暴露 `status='active'` 的家庭，停用家庭不能调用家庭钱包接口。
- 真实 MySQL 并发测试：两个首次查询请求同时面对缺失钱包时均成功且最终只有一条账户记录；两个首次资金操作同时初始化同一钱包时不死锁、最终只有一条账户且余额变化守恒。
- 真实 MySQL 已有钱包回归：两个并发资金操作继续使用原钱包行锁顺序，不发生重复键锁升级或死锁；现有 `twoFreezesCannotOverdrawOneFamilyBalance` 等竞态测试必须在引入初始化器后继续通过。
- 运行钱包相关后端测试和后端完整测试集。

## 验收

- 有效家庭首次请求 `/family/wallet` 不再因缺少账户记录返回 404。
- 同一家庭并发首次访问最多形成一条钱包记录。
- 已有钱包余额不变。
- 无钱包的无效或停用家庭不会被初始化；家庭端停用家庭由实时身份层拒绝进入钱包接口。
- 当前业务数据库不执行批量迁移。
