# 家庭钱包按需初始化设计

## 问题

`GET /family/wallet` 路由已注册，但已加入家庭的用户仍可能收到 HTTP 404。钱包表由历史迁移流程填充，而当前迁移模式为 `OFF`，家庭创建流程也不保证创建 `family_wallets` 记录，因此业务层抛出“家庭钱包不存在”。

## 目标

在不执行批量迁移、不修改已有钱包余额的前提下，为缺少钱包记录的有效家庭按需创建零余额家庭钱包，并让查询与订单资金操作使用相同的账户存在性保障。

## 方案

### 持久化

在 `FamilyWalletMapper` 增加幂等方法 `insertAccountIfMissing(familyId)`。SQL 使用：

```sql
insert ignore into family_wallets(family_id, available_amount, frozen_amount)
select id, 0, 0
from families
where id = #{familyId} and status = 'active'
```

该语句只会为存在且启用的家庭创建账户；已有记录不更新，余额和版本均不改变；并发请求依赖家庭钱包主键和 `insert ignore` 收敛为一条记录。

### 服务

`FamilyWalletServiceImpl.get(familyId)`：

1. 先查询钱包，保持正常读路径无额外写入。
2. 缺失时执行幂等初始化，再查询一次。
3. 二次查询仍缺失时返回现有“家庭钱包不存在”错误，覆盖无效或停用家庭。

`FamilyWalletServiceImpl.lockAccount(familyId)`：

1. 先尝试锁定钱包。
2. 缺失时执行同一幂等初始化，再重新 `select ... for update`。
3. 仍缺失时返回现有错误。

这样查询、冻结、扣款、释放和退款都共享相同保障，不产生只修查询、不修下单的分叉行为。

## 数据安全

- 不运行家庭钱包迁移器或任何批量数据脚本。
- 不读取、汇总或清空个人钱包。
- 不覆盖已有家庭钱包的可用余额、冻结余额和版本。
- 每次只处理当前业务请求关联的单个有效家庭。
- 对不存在或停用的家庭不创建钱包。

## 测试

- Mapper SQL 契约：必须从 `families` 选择有效家庭，使用 `insert ignore`，且初始余额均为 0。
- 服务测试：钱包已存在时不初始化；钱包缺失时初始化后返回零余额账户；无效家庭初始化后仍缺失时继续返回 404。
- 锁定路径测试：钱包缺失时初始化后可获取锁定账户，确保下单资金流程同样有效。
- 运行钱包相关后端测试和后端完整测试集。

## 验收

- 有效家庭首次请求 `/family/wallet` 不再因缺少账户记录返回 404。
- 同一家庭并发首次访问最多形成一条钱包记录。
- 已有钱包余额不变。
- 无效家庭仍返回原有 404。
- 当前业务数据库不执行批量迁移。
