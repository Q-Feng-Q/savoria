# 小程序交付稳定性审查设计

## 1. 背景与目标

当前小程序已经完成暖色动物私厨风格重构，并持续补充了家庭、共享餐篮、家庭钱包、商户菜品、订单、推荐菜和资料编辑等业务能力。现有自动化测试基线为：

- 小程序：37 个页面、11 个服务模块，`npm test` 共 348 项全部通过。
- 后端：`mvn test` 共 285 项通过，0 项失败，12 项依赖 Docker/MySQL 的测试因当前环境不可用而跳过。

测试通过并不等同于可交付。此前仍出现过前端调用不存在接口、页面只显示部分数据、页面返回后不刷新、空值直接显示为 `NULL`、微信原生 `button` 造成布局异常、WXML/WXSS 编译失败等问题。本次工作的目标是对“小程序全部页面及其对应后端接口”进行一次交付前稳定性审查，补齐可自动发现这些问题的契约测试，并修复审查中发现的缺陷。

## 2. 范围

### 2.1 纳入范围

审查覆盖 `frontend` 小程序的全部 37 个页面、11 个服务模块，以及这些页面实际调用的 `backend` 控制器、应用服务和响应模型，按以下业务域组织：

1. 登录与账号：登录、注册、账号切换、角色/权限入口、账号管理、通知权限。
2. 家庭端：主页、家庭加入与创建、家庭信息、成员与管理员移交、地址、钱包、共享餐篮、点菜、菜品详情、订单列表与详情。
3. 商户端：工作台、商户资料、家庭管理、家庭详情、菜单配置、菜品管理、系统菜品导入、推荐菜、订单与采购。
4. 公共基础：请求封装、会话恢复、路由参数、加载/空/错误状态、自定义按钮、响应式布局、安全区与 WXML/WXSS 编译兼容。

具名页面与服务基线见附录 A。实施时生成“页面 → 服务函数 → HTTP 方法/路径 → 后端控制器方法 → 授权范围”机器可读清单，并自动校验 `app.json` 注册页、实际页面目录、服务导出和清单一致；出现未登记页面、请求或后端入口时测试失败。

### 2.2 不纳入范围

- 不审查或重构 `admin-web` 管理后台。
- 不进行新的大范围视觉设计，继续使用现有“暖暖动物私厨”视觉体系。
- 不新增本次交付稳定性无关的业务能力。
- 不在当前业务数据库执行迁移、清理、修复或写入操作。
- 不为通过审查而进行无关架构重写。

## 3. 审查方案

采用“契约优先的全量审查”，由四层检查组成。

### 3.1 前后端接口契约检查

建立可重复执行的接口清单，将小程序服务模块中的请求与后端控制器逐项对应，检查：

- 请求路径及动态路径参数是否存在。
- HTTP 方法是否一致。
- query、path、body 字段是否匹配，必填值是否可能传入 `null`、`undefined` 或空字符串。
- 鉴权角色与页面入口是否一致，家庭用户不能误入商户接口，商户负责人能获得应有入口。
- 列表分页是否被前端误当成全量数据，是否需要继续拉取后续页面。
- 响应字段、枚举和空值是否被页面正确转换为可读展示。
- 请求适配器最终生成的 `Content-Type`、query 编码、动态路径编码、JSON 序列化、日期/时间与枚举值是否符合控制器请求模型。

接口清单作为测试资产维护，后续新增前端请求但缺少后端路由时应直接失败，而不是等到微信开发者工具运行后才发现 404。每个请求至少具备一个有效请求形态契约；对存在必填字段、动态路径、枚举或日期的请求补充代表性无效请求，断言精确 HTTP 状态、稳定业务错误结构且不泄露内部异常。后端路由清单同时反向核对前端实际调用，避免只验证单侧声明。

分页场景使用数量大于接口默认页大小的数据集，断言稳定排序、逐页终止、无重复、无遗漏；导入、家庭菜单候选菜品和成员选择等要求全量结果的界面，还必须断言确实消费所有页面而非只取第一页。

### 3.2 页面行为与数据新鲜度检查

逐页检查页面生命周期和交互状态：

- 首次进入、返回页面、切换账号/角色、完成新增/编辑/上下架/推荐/配置后是否重新加载正确数据。
- 页面是否区分加载中、真实空数据、权限不足和请求失败，避免失败被误显示为“暂无数据”。
- 写操作是否有防重复提交、禁用态、成功反馈和失败恢复。
- 列表、详情和首页摘要是否使用一致数据源，避免新增菜品后某一页面仍保留旧缓存。
- 页面跳转、返回和路由参数是否完整，避免 `undefined`/`null` 拼入 URL。
- 共享餐篮、家庭钱包和预计用餐时间继续遵循当前业务架构，不恢复个人钱包或早/午/晚餐次逻辑。

对适用页面建立具名刷新矩阵，至少覆盖“执行新增/编辑/状态变更 → 返回列表或触发 `onShow` → 发起新请求 → 新数据可见”。账号或角色切换必须清理身份相关缓存，并断言旧身份的家庭、商户、菜单、餐篮和订单数据不会继续显示或短暂闪现。

### 3.3 模板、样式与多尺寸检查

对全部页面进行静态编译兼容与响应式审查：

- 按用户已确认的界面规范，普通业务操作不得直接使用微信原生 `button`，继续使用项目自定义按钮组件；若未来必须依赖仅由 `button open-type` 提供的平台能力，需要单独规格与用户批准，不在本次工作中自行引入。自定义按钮必须具备可访问名称、明确禁用态、防重复点击和至少 44px 等效点击区域。
- 检查非法 WXML 指令组合、复杂表达式、未闭合标签和 WXSS 不兼容语法。
- 检查按钮文字、前景色与背景色对比度，不能出现按钮与背景难以区分。
- 检查长名称、长电话号码、金额、多行说明、空图片和错误图片下的布局。
- 覆盖 320×568、375×667、390×844、430×932 四组竖屏 viewport，并模拟 0px 与 34px 底部安全区；主要操作不能被固定栏、胶囊按钮或刘海区域遮挡。
- 保持现有暖色、奶油色、鼠尾草绿与珊瑚橙体系，不引入大面积无关插画或不一致组件风格。

这部分以可自动检查的模板/样式契约为主，并用两倍常规长度的名称/说明、最长联系电话/金额、缺图和图片加载失败作为压力数据。每组检查记录：页面无横向溢出、正文不被裁切、主要操作完整可见且可点击、底部内容可滚动至安全区之上。无法可靠自动判断的视觉问题形成明确人工检查清单，不以脆弱的像素快照替代真实验收。

WXML/WXSS 先由仓库内静态兼容测试覆盖全部页面文件，最终还必须通过当前微信开发者工具的完整编译，以“0 个 WXML/WXSS 编译错误、37 个页面无遗漏”为通过标准。若环境没有可调用的开发者工具 CLI，则记录版本并执行一次 GUI 全量编译；该步骤未完成时只能报告代码与静态测试完成，不能宣称微信编译验收完成。

### 3.4 后端业务与授权检查

对小程序依赖的后端入口检查：

- 控制器路由、请求对象、鉴权和应用服务调用链完整。
- 家庭、商户和账号上下文从当前登录身份实时获取，不能依赖过期前端缓存授予权限。
- 建立“当前身份 × 资源归属（本家庭/其他家庭、本商户/其他商户）× 读写操作”授权矩阵，覆盖伪造资源 ID、已切换/失效会话和跨租户访问；越权请求不得返回或修改目标数据，错误响应不得泄露资源是否存在或内部堆栈。
- 列表查询具备稳定排序和合理分页；全量选择场景必须支持完整加载。
- 新增/编辑/上下架/审核/推荐/菜单配置/订单状态变更后，关联查询能够读取最新结果。
- 业务异常返回稳定错误码与可展示消息，不能以 404 掩盖未实现接口或以 500 暴露内部异常。
- 家庭钱包、共享餐篮与订单冻结/扣款继续遵循已迁移后的家庭级资金模型。

## 4. 缺陷处理原则

1. 先复现：每个确认缺陷先补一个最小失败测试或契约检查，记录触发条件。
2. 查根因：判断问题位于页面状态、服务封装、接口路由、响应映射、权限或持久化查询，不在表象处重复打补丁。
3. 最小修复：只修改解决问题所需的边界，保留现有业务和视觉设计。
4. 防回归：修复后运行目标测试、所在业务域测试以及前后端完整测试。
5. 保护用户改动：主工作树现有未提交的共享餐篮修改不覆盖、不清理；本次工作在独立工作树完成后再安全合并。
6. 数据安全：数据库验证只允许测试专用 profile 下的内存数据库或一次性 Testcontainers 数据库。测试启动时校验 JDBC URL、数据库名和 profile，发现非测试地址立即失败；容器使用专用最小权限凭据。不对当前业务数据库执行变更。

## 5. 优先级

- P0：无法编译/启动、数据破坏、越权、扣款或订单状态错误。
- P1：接口 404/400/500、核心流程不可完成、列表数据缺失、角色入口错误、操作后不刷新。
- P2：空/错/加载状态错误、参数丢失、重复提交、明显多尺寸布局或按钮可读性问题。
- P3：不阻断流程的文案、间距和视觉一致性问题。

按 P0 → P1 → P2 → P3 处理；同级问题优先修复点菜、餐篮、提交订单、商户菜品和订单处理等核心链路。

## 6. 验收标准

交付前必须满足：

1. 小程序全部现有测试和本次新增审查测试通过；保留 348 项基线测试，新增数量单独记录，测试减少或 disabled 必须逐项解释。
2. 后端全部现有测试和本次新增测试通过；保留 285 项基线测试，新增数量单独记录，全部 skipped/disabled 项列出原因。钱包、扣款、餐篮、订单提交与订单状态流转的关键 MySQL 持久化测试未执行时，不得宣称完整可交付，只能标记为等待环境验收。
3. 小程序服务请求与后端路由之间无未解释的路径或方法缺口。
4. 附录 A 的 37 个页面均出现在机器可读映射中，具备适用的加载、空、错误、权限和刷新行为；映射与实际目录、`app.json`、服务导出自动一致。
5. 不存在微信原生 `button` 回归；当前微信开发者工具完整编译为 0 个 WXML/WXSS 错误；四组 viewport 与两组安全区检查无横向溢出、内容裁切或主要操作遮挡。
6. 核心用户流程通过针对性验证：登录与切换身份、家庭资料与成员、点菜与共享餐篮、家庭钱包与下单、商户菜品与菜单、推荐菜、商户订单状态流转。
7. 修复代码通过独立代码审查，不引入无关重构，不覆盖主工作树用户改动。

## 7. 交付物

- 可执行的接口与页面契约测试。
- 审查中发现问题的最小修复及回归测试。
- 一份交付验证摘要，列出测试数量、跳过项、修复范围和仍需真实微信设备/外部环境验证的项目。
- 经验证的代码提交，合并回当前开发分支前再次检查主工作树差异。
