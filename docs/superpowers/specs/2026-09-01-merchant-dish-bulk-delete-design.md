# 商户菜品批量删除与恢复设计

## 目标

在小程序商户端菜品管理页提供批量逻辑删除、回收站查看和批量恢复功能。已删除菜品从商户日常列表、家庭菜单配置和客户端点菜入口消失，但保留菜品资料和历史订单快照，支持审计与恢复。

## 范围

- 小程序页面：`frontend/pages/merchant/merchant-dishes/index`。
- 后端菜品模块、家庭菜单可见性和餐篮新增校验。
- 新增 `V12__add_dish_logical_deletion.sql` 前向 Flyway 迁移，不修改既有迁移，不物理删除菜品、配方、步骤或历史订单数据。
- 不在本次提供永久删除。

## 数据模型

`dishes` 增加：

- `deleted_at datetime(6) null`：逻辑删除时间。
- `deleted_by bigint null`：执行删除的用户 ID。
- 索引 `idx_dishes_merchant_status_deleted (merchant_id,status,deleted_at,id)`。

删除时间使用 `CURRENT_TIMESTAMP(6)`。逻辑删除使用 `status='deleted'`。有效业务状态仍为 `active` 和 `inactive`；恢复统一进入 `inactive`，并清空 `deleted_at`、`deleted_by` 和推荐时间。数据库写入必须维持不变量：`deleted` 状态的两个审计字段非空，`active/inactive` 状态的两个审计字段为空。恢复不自动重新启用任何家庭菜单。

`DishEntity`、菜品视图、MyBatis `resultMap` 及所有显式菜品列清单同步增加审计字段。回收站查询通过 `LEFT JOIN users` 解析操作人，展示名优先使用 `nickname`，其次 `username`，均不可用时显示“用户 {deleted_by}”。

## 后端接口

### 批量删除

`POST /merchant/dishes/batch-delete`

请求 JSON 固定为 `{ "dishIds": [1, 2] }`。原始数组长度必须为 1–100；上限在去重前校验。每个 ID 必须非空且为正数，随后由服务端保持首次出现顺序去重：

- 菜品必须存在且属于当前商户。
- 混入其他商户、非法或不存在的 ID 时整批失败。
- 已删除菜品按幂等项处理，且不得覆盖其首次 `deleted_at/deleted_by`。

在同一事务内将目标菜品标记为 `deleted`，写入删除时间和当前用户，清空推荐状态，并将所有匹配的 `family_menu_items.enabled` 设为 `0`。家庭菜单行的家庭价和排序保留，确保可审计；删除、恢复再重新上架后也不会自动出现在家庭菜单。

删除同时把目标菜品尚未完成的 `dish_review_submissions` 关闭为 `REJECTED`，审核原因记录“菜品已删除”；已提交的平台模板同步申请不修改平台模板，也不得再回写已删除商户菜品。所有审核批准路径仍必须在持锁后拒绝 `deleted` 目标，避免并发审批将菜品复活。

### 批量恢复

`POST /merchant/dishes/batch-restore`

请求 JSON、校验和去重规则与批量删除相同。已删除菜品恢复为 `inactive` 并清空删除审计字段；未删除菜品按幂等项处理。恢复后必须先上架，再由商户重新配置家庭菜单。

两个接口均返回 `{ "requestedCount": 2, "uniqueCount": 2, "changedCount": 1, "unchangedCount": 1 }`（位于统一 `ApiResponse.data` 中），并补充到 `docs/api-spec.md`。

### 查询

商户菜品查询新增显式范围参数：

- 缺省或 `scope=available` 排除 `deleted`。
- `scope=deleted` 仅返回回收站菜品，并返回删除时间与删除操作人展示名称。
- 其他 `scope` 值返回参数错误。

普通菜品详情、编辑、上下架、推荐、模板同步等写接口均拒绝已删除菜品。家庭菜单配置、客户端点菜菜单、菜品详情和餐篮新增均不得接受已删除菜品。

## 小程序交互

普通菜品列表和回收站均使用自定义 `view` 复选框，不使用微信原生 `button`：

1. 每道菜左侧提供选择框。
2. “全选当前列表”仅作用于经过搜索及状态筛选后实际显示的行。
3. 普通列表显示“批量删除（N）”；回收站显示“批量恢复（N）”。
4. 切换筛选、切换普通列表/回收站或重新加载时清空选择。
5. 删除前弹出确认框，显示数量并说明菜品将从家庭菜单和客户端点菜中隐藏。
6. 回收站行展示删除时间和操作人，禁用编辑、上下架、推荐和模板同步入口。

删除、恢复、上下架、推荐和模板同步共用单一页面级写锁，替换或统一协调现有 `busyDishMap` 与 `syncBusyDishMap`。任一写操作未结束时，所有写处理器必须在发请求前返回，全部对应控件绑定禁用、`aria-disabled` 和忙碌状态。

复选框使用 `aria-role="checkbox"`、`aria-checked`、`aria-disabled`、`aria-busy` 和按压反馈，处理器再次检查禁用状态，触控宽高不少于 `88rpx`。搜索词、状态筛选或列表范围任一变化时均清空选择，防止隐藏 ID 残留。

页面采用非乐观更新：成功后重新读取服务器状态并清空选择；失败时列表、可见状态和选择保持不变。空选择和超过 100 项时前端不发请求。

## 响应式布局

批量工具栏允许换行；选择框保持固定触控尺寸，菜名和价格区域可收缩，操作区在窄屏下独占下一行，保证不横向溢出。继续沿用现有暖色动物厨房视觉和自定义交互控件。

## 锁顺序与并发

所有会读取或改变菜品可用性的事务使用一致顺序：锁定商户行，再按 ID 升序锁定菜品行，随后才锁定/修改家庭菜单或餐篮行。批量删除/恢复、菜品编辑、状态、推荐、制作步骤、菜品审核提交与批准、模板同步、家庭菜单保存/复制和餐篮加菜都必须在写入前于事务内重新检查菜品未删除。

家庭菜单保存/复制与批量删除共用商户锁；餐篮加菜从家庭解析商户后遵循相同商户→菜品→家庭菜单→餐篮顺序，并使用带锁的可用性读取。这样删除与加菜竞态只能产生两种确定结果：加菜先提交后该餐篮行转为不可用，或删除先提交后加菜被拒绝。

## 历史数据、餐篮与订单

订单条目继续使用现有订单快照展示菜名、价格和成员明细，不依赖菜品当前状态。逻辑删除不修改历史订单、采购或钱包流水。恢复也不会回写历史记录。

菜品删除前已存在的餐篮行继续展示其名称、价格和成员选择，并标记“菜品已删除，不可提交”；用户可减少数量或移除，但不能增加数量。提交订单时继续在事务内校验菜品与家庭菜单可用性，只要餐篮含不可用菜品就整体拒绝，并返回可识别的业务错误。

## 错误处理

- 请求为空、超过 100 项或含非法 ID：返回参数错误。
- 含越权或不存在菜品：整批拒绝并回滚。
- 并发删除/恢复及其他菜品写入：遵循统一锁顺序和事务内状态复查，操作保持幂等。
- 页面请求失败：显示明确提示，不清空选择，不改变可见列表。

## 测试与验收

后端测试覆盖：

- 批量删除、批量恢复及商户权限隔离。
- 1–100 条边界、空请求、重复 ID、越权和不存在 ID。
- 整批事务、幂等行为、删除审计字段、恢复为下架状态。
- 重复删除保留首次审计字段；非删除状态始终清空删除审计字段。
- 删除取消推荐并停用家庭菜单；覆盖删除→恢复→上架后仍不会自动重新启用家庭菜单。
- 默认列表、回收站范围、非法 `scope`、操作人名称回退和响应计数正确。
- 删除自动关闭待审核菜品变更，审核批准、模板同步和所有菜品写接口拒绝已删除菜品。
- 家庭菜单、客户端菜单/详情和餐篮新增拒绝已删除菜品。
- 已有餐篮行保持可见且可移除，不可增加或提交；删除与加菜竞态结果确定。
- 历史订单快照读取不受影响。
- 用 MySQL Testcontainers 从完整 Flyway 迁移链验证 V12；不以已禁用 Flyway 的 H2 测试替代。

前端测试覆盖：

- 当前筛选结果的单选、全选、取消全选和计数。
- 删除确认、批量删除、回收站与批量恢复。
- 每次有效批量操作只发送一次请求并传递去重后的 ID。
- 空选择、超过上限、取消确认不发请求。
- 失败保持列表和选择，成功重新加载并清空选择。
- 延迟 Promise 验证页面级写锁阻止第二个写请求。
- 不引入原生 `button`，复选框 ARIA、处理器禁用守卫、至少 `88rpx` 触控尺寸和窄屏布局符合约束。
- 商户服务测试及 delivery service/page-operation 契约清单包含查询范围、批量删除和批量恢复。

验证时运行后端和前端完整测试；仅验证 Flyway 脚本与测试数据库兼容性，不连接或修改当前业务数据库。
