# 家庭菜单批量启用设计

## 目标

在小程序商户端的家庭菜单配置页补充快速启用能力，解决商户需要逐项启用菜品的问题。支持一键启用全部在售菜品，以及通过复选框选择菜品后批量启用。

## 范围

- 页面：`frontend/pages/merchant/family-menu/index`。
- 沿用现有家庭菜单读取与保存接口，不新增数据库表或迁移。
- 只改变菜品的家庭菜单启用状态，不修改家庭价、排序和商户菜品上架状态。
- 不实现批量停用、跨家庭操作或服务端新增批量接口。

## 页面与交互

页面工具区提供以下操作：

1. “全选当前列表”复选框：选中当前 `getFamilyMenu` 请求返回并进入 `menuDraft` 的全部菜品；再次点击取消全选。
2. 每道菜左侧提供自定义复选框。单项选择变化后同步更新已选数量和全选状态。
3. “批量启用（N）”：仅将已选菜品设置为启用。未选择菜品时按钮禁用，并阻止请求。
4. “一键启用全部”：将当前 `menuDraft` 中的全部菜品设置为启用，不要求提前勾选。现有家庭菜单读取接口是本功能中可配置菜品的唯一来源，不额外推断菜品上架状态。

已启用菜品允许被选中；批量启用是幂等操作，不改变其价格和排序。批量操作成功后清空选择并重新读取服务器数据。

## 数据流与一致性

页面继续维护完整的 `menuDraft`。批量操作从当前草稿复制出新草稿，只修改目标条目的 `enabled` 字段，然后通过现有 `saveFamilyMenu(familyId, { items })` 一次提交完整菜单。每次有效的批量操作只调用一次保存接口，使用当前已解析的 `familyId`；提交条目的数量、顺序、`dishId`、`familyFinalPrice`（包括数值 `0`）和 `sortOrder` 必须原样保留。

所有会提交完整菜单的动作共用一个页面级写锁，包括一键启用、批量启用、逐项启停、家庭价调整和复制家庭菜单。任一写请求进行中时，其他写处理器必须在发请求前直接返回；对应自定义控件同时绑定禁用、`aria-disabled` 和忙碌状态，避免完整草稿之间发生后写覆盖。

批量启用采用非乐观更新：请求期间 `menuRows` 保持服务器上次确认的可见状态，内部只准备待提交草稿。保存成功后重新加载家庭菜单，以服务器结果更新 `menuDraft` 和 `menuRows`，并清空选择；保存失败时保留原 `menuDraft`、原 `menuRows` 和原选择，显示失败提示。

## 边界与错误处理

- 菜单为空时隐藏或禁用批量工具，并展示现有空状态。
- 未选择任何菜品时不发送批量启用请求。
- 全部菜品均已启用时，一键启用全部不重复提交，提示“全部菜品已启用”。
- 页面首次加载、手动重试、家庭切换或保存成功后重新加载时清空已选集合，防止选择状态串到另一家庭。
- 复选框和按钮继续使用项目自定义 `view` 控件，不使用微信原生 `button`。

## 测试与验收

新增或扩展前端测试，覆盖：

- 单项选择、取消选择及已选数量。
- 全选当前列表与取消全选。
- 批量启用只修改选中条目，并保留价格和排序。
- 一键启用全部修改全部条目。
- 每个有效批量动作只请求一次保存接口；断言家庭 ID、条目数量和顺序不变，所有 `dishId`、家庭价（含 `0`）和排序不变，只有目标条目的 `enabled` 可以变化。
- 空选择与全部已启用时不发请求。
- 保存失败时内部草稿、可见启用状态和选择均保持不变。
- 保存成功后重新读取并清空选择；普通重试加载和家庭切换也分别验证会清空选择。
- 使用延迟 Promise 验证首个写请求未结束时，第二个批量、逐项、价格或复制动作不会发出请求。
- WXML 不引入原生 `button`；所有选择、逐项、价格及批量控件在写锁期间不可操作并暴露正确 ARIA 状态；小屏宽度下工具区可换行且不横向溢出。
